What these checks do—and do not—prove

uptime reports time since boot, logged-in users and load averages. systemctl queries Linux services; is-active ssh asks whether the SSH server is running now.

A successful connection demonstrates usable SSH access from the desktop. These checks do not prove future availability, complete security or that SSH is configured to start on every future boot.

Current boundary: the Archer is an access point on the home LAN, so this is not an isolated subnet. The earlier OS baseline identified Debian 13. Pi-hole installation is user-reported; dashboard access has since been browser-observed. The controlled DNS cycle, rule cleanup and structural configuration-backup checks are complete. Restore testing and household rollout remain future work.

Make it stick: one minute, three questions

Try answering aloud before opening each answer. Check the explanation, correct one gap and continue. No score or gate.

1. Why did restarting close SSH? What showed the Pi returned?

Restarting stops the remote system and its network connection. Reconnecting, seeing 17 minutes of uptime and finding SSH active support recovery during this sequence.

2. Why use both uptime and the SSH service check?

They answer different questions: “How long since boot?” and “Is SSH running now?” Neither alone demonstrates that the desktop can log in. Our successful connection adds that practical evidence.

3. How are apt update and apt full-upgrade different?

apt update refreshes the list of available packages. apt full-upgrade installs upgrades and resolves dependencies; it may remove packages, so review its proposed changes. A list of 14 available upgrades is not proof that 14 were installed.

Revisit: recall these at the next session, then about a week later. Adjust if a concept is uncertain. These are suggested intervals, not a proven optimal schedule; this page creates no reminders.

Why this memory method?

Brief recall, corrective feedback and spaced review can support retention. The U.S. Department of Education's learning guide recommends retrieval, spacing and explanatory questions. Roediger and Karpicke's study found better delayed recall after testing than repeated study in prose-learning experiments. Applying those principles here is a teaching choice, not a promise of instant memory or IT mastery.

The base list combines adware and malware domains; optional gambling, pornography and social-media extensions are separate. Start with this one list so a problem is easier to trace. False positives remain possible, and DNS filtering cannot remove every ad.

DNS history can include domains, clients, timestamps and outcomes, but not HTTPS page contents or full URL paths. Keep raw history private; publish deliberate test evidence. Query-file logging has separate controls from FTL privacy and database retention: No alone does not disable all history.

Level 0 preserves detailed FTL statistics, helping trace a test domain to its requesting device. Higher levels hide domains, then clients, or retain only anonymous statistics. Review privacy and retention before household rollout; these FTL controls are separate from query-file logging.

The 18 October Windows screenshot shows the lookup below. The public command replaces the actual Pi address with YOUR_PI_IP:

nslookup -type=A example.com YOUR_PI_IP

nslookup requests a DNS record; -type=A requests an IPv4 address, and the final argument explicitly chooses the Pi as resolver. This one lookup does not change Windows or router DNS settings. Microsoft documents the command syntax.
